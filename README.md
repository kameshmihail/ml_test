
# README : Инструкция по запуску

## 1. Требования к окружению
### 1.1. Необходимый стек
- **Python 3.9+** 
- **Интерпретатор**: локальный терминал, Jupyter Notebook или Google Colab
- **Стабильное интернет-соединение** (для вызова OpenRouter API)
### 1.2. Установка зависимостей
Выполните в терминале при отсутствии библиотек:

pip install openai pandas numpy matplotlib scipy tenacity
(уже есть в ipynb исходнике)


----------

## 2. Получение API ключа OpenRouter

1.  Перейдите на сайт: [https://openrouter.ai/](https://openrouter.ai/)
    
2.  Зарегистрируйтесь (можно через Google или GitHub)
    
3.  Перейдите в раздел **Keys**: [https://openrouter.ai/keys](https://openrouter.ai/keys)
    
4.  Нажмите **"Create Key"**
    
5.  Скопируйте полученный ключ (начинается с `sk-or-v1-...`)
    

> **Важно**: Бесплатные модели имеют лимиты. Если вы превысите лимиты, система автоматически переключится на следующую модель из списка `FREE_MODELS`.

----------

## 3. Настройка API ключа в коде

Откройте файл `ipynb` и замените строку:



OPENROUTER_API_KEY = "YOUR_API_KEY_HERE"

**На свой ключ:**


OPENROUTER_API_KEY = "sk-or-v1-ВАШ_КЛЮЧ"

## 4. Запуск агента (для Jupyter/Colab)


Скрипт предложит выбрать режим:

    ==================================================
    ВЫБОР РЕЖИМА РАБОТЫ
    ==================================================
    1 - Сгенерировать новые данные и выполнить анализ
    2 - Загрузить локальный data.csv и выполнить анализ
    --------------------------------------------------
    Ваш выбор (1 или 2):

**Режим 1 (Генерация данных):**

- Создаётся синтетический датасет на 1000 пользователей × 12 месяцев
- Выполняется полный анализ
- Данные экспортируются в `data.csv` и `metrics.csv`

**Режим 2 (Загрузка локальных данных):**

- Агент ищет файл `data.csv` в текущей директории
- Проверяет наличие обязательных колонок
- Выполняет анализ на загруженных данных


## 5. Формат входных данных (режим 2)

Если вы используете режим **2 (загрузка локальных данных)**, файл `data.csv` должен содержать следующие колонки:

| Колонка | Тип | Описание | Пример |
|---------|-----|----------|--------|
| `user_id` | int | ID пользователя (1..N) | 42 |
| `month` | int | Номер месяца (1..12) | 5 |
| `plan` | str | Тарифный план | "pro" |
| `monthly_price` | float | Цена тарифа | 19.99 |
| `payment_status` | str | Статус платежа | "paid" / "failed" |
| `amount_paid` | float | Фактическая сумма платежа | 19.99 |
| `is_active` | bool | Активен ли аккаунт | True / False |

**Пример строки:**

    user_id,month,plan,monthly_price,payment_status,amount_paid,is_active
    1,1,basic,9.99,paid,9.99,True
    1,2,basic,9.99,paid,9.99,True
    1,3,basic,9.99,failed,0.0,True
    2,1,pro,19.99,paid,19.99,True
    2,2,pro,19.99,failed,0.0,False

## 7. Возможные ошибки и их решение

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `ImportError: No module named 'openai'` | Не установлены зависимости | Выполните `pip install openai pandas numpy matplotlib scipy tenacity` |
| `FileNotFoundError: data.csv` | Режим 2, но файл отсутствует | Переключитесь на режим 1 (генерация) или создайте CSV |
| `ValueError: missing required columns` | В CSV не хватает колонок | Добавьте все 7 обязательных колонок (см. раздел 5) |
| `All models unavailable` | API ключ неверный или истёк лимит | Проверьте ключ в OpenRouter, создайте новый |
| `429 Rate limit` | Превышен лимит бесплатной модели | Агент автоматически переключится на следующую модель |
| `402 Payment required` | Модель требует оплаты | Агент автоматически пропустит эту модель |
| Ошибка при загрузке данных | Неверный формат CSV | Убедитесь, что разделитель — запятая, нет BOM |

## Сноска: Допущения интерпретации данных

При анализе метрик подписочного сервиса в рамках данного агента действуют следующие допущения:

### 1. Определение активных пользователей
Активным считается пользователь, чей аккаунт не закрыт и не заблокирован. При этом:
- Пользователь может быть активным, но не платить в текущем месяце (grace period, технические проблемы с биллингом, оспаривание платежа)
- Отток (churn) фиксируется ТОЛЬКО при смене статуса `is_active` с True на False
- Пропуск платежа без деактивации НЕ считается оттоком

### 2. ARPU (Average Revenue Per User)
В данной реализации **ARPU = monthly_revenue / paid_users**, а НЕ на всех активных пользователей. Это сознательное допущение, основанное на следующих соображениях:
- Метрика «выручка на платящего пользователя» лучше отражает монетизацию активной платящей базы
- Разбавление ARPU за счёт неплатящих активных пользователей (grace period) искажает реальную картину доходности
- Для анализа эффективности тарифных планов важнее понимать, сколько платит тот, кто действительно платит

Альтернативный расчёт (ARPU на active_users) может быть легко добавлен при необходимости.

### 3. Churn rate
Формула расчёта: `churn_rate = churned_users / active_users(prev_month) * 100%`, где:
- `churned_users` — пользователи, бывшие активными в предыдущем месяце и ставшие неактивными в текущем
- Пользователи, которые никогда не были активны, не учитываются в расчёте оттока
- Повторный возврат пользователя (реактивация) в данной модели не предусмотрен

### 4. Переход между тарифными планами (Upgrade / Downgrade)
**Допущение:** В текущей версии агента **миграция пользователей между тарифными планами отсутствует**.
- Каждый пользователь закреплён за одним тарифом (`basic`, `pro`, `premium`) на весь период жизни
- Тариф назначается при генерации данных и не меняется
- `monthly_price` остаётся константой для каждого пользователя
- Рост ARPU на фоне падения активной базы может объясняться не апсейлами, а «вымыванием» дешёвых пользователей

### 5. Новые пользователи (New user acquisition)
**Допущение:** В текущей версии агента **приток новых пользователей отсутствует**.
- Все пользователи начинают в месяц 1 и либо остаются активными, либо отваливаются
- Нет пополнения базы новыми подписчиками в месяцах 2–12

**Рекомендация при интерпретации:**
- Если в данных появляются новые пользователи, проверка `active_users_monotonically_decreasing` покажет 0 (false)
- Агент не рассчитывает LTV (Lifetime Value) когорт, пришедших в разные месяцы
- Для анализа с новыми пользователями необходима модификация логики расчёта оттока (когортный анализ)

### 6. Синтетические данные
При использовании режима 1 (генерация данных) действуют следующие допущения:
- В первом месяце все пользователи активны и успешно платят (100% payment success rate)
- Вероятность оттока растёт линейно с каждым месяцем: `base_churn = 0.03 + ((month - 1) / total_months) * 0.25`
- Индивидуальный риск оттока зависит от тарифного плана:
  - Basic: повышенный риск (коэффициент 1.2)
  - Pro: пониженный риск (коэффициент 0.8)
  - Premium: минимальный риск (коэффициент 0.5)
- Вероятность успешного платежа при активной подписке — 95%
- В случае неудачного платежа пользователь остаётся активным (grace period)

### 7. Проверки качества данных
Проверки качества (раздел 5 отчёта) используются ИСКЛЮЧИТЕЛЬНО для оценки достоверности датасета. При формировании разделов 1-4 и 6:
- Данные считаются достоверными для анализа
- Наличие ошибок в проверках качества не отменяет бизнес-выводы, но снижает доверие к ним

### 8. Ограничения LLM
LLM в рамках данного агента:
- НЕ выполняет математические расчёты (это сделано кодом)
- НЕ вычисляет проценты роста (MoM%, CAGR)
- НЕ придумывает причины изменений метрик (только из данных)
- Использует ТОЛЬКО абсолютные значения из таблицы

### 9. Временные допущения
- Месяцы нумеруются последовательно с 1
- Отсутствует сезонность и праздничные эффекты
- Нет акций, скидок или промо-периодов

### 10. Соответствие amount_paid и monthly_price

**Допущение:** В корректных данных `amount_paid` должна строго соответствовать `monthly_price` при успешном платеже.

| Сценарий | Ожидаемое поведение | Проверка качества |
|----------|--------------------|--------------------|
| `payment_status = 'paid'` | `amount_paid = monthly_price` | `paid_status_amount_mismatch` |
| `payment_status = 'failed'` | `amount_paid = 0` | `failed_status_nonzero_amount` |

- **Частичные платежи**: В реальных сервисах возможны частичные списания (недостаточно средств на карте, частичный рефанд). Агент считает это ошибкой.
- **Скидки и промо-коды**: Реальная сумма платежа может быть меньше `monthly_price` (промо-период, скидка за год вперёд). Агент пометит это как несоответствие.
- **Штрафы и пени**: Начисление пени за просрочку увеличит `amount_paid` сверх `monthly_price` — будет зафиксировано как mismatch.
- **Технические ошибки биллинга**: Списание неверной суммы — проблема, которую агент выявляет.

**Как агент обрабатывает несоответствия:**

1. Проверка `paid_status_amount_mismatch` подсчитывает количество строк, где `payment_status='paid'`, но `amount_paid != monthly_price`
2. Проверка `failed_status_nonzero_amount` подсчитывает строки, где `payment_status='failed'`, но `amount_paid != 0`
3. Эти проверки включаются в раздел 5 отчёта (Data Quality Checks)
4. LLM получает описание каждой проверки и может рекомендовать аудит биллинговой системы

### Когда допущения могут повлиять на выводы
| Ситуация | Потенциальное искажение | Рекомендация |
|----------|------------------------|--------------|
| Высокий процент неплатежей при активном статусе | ARPU завышен относительно общей базы | Рассчитать ARPU на active_users дополнительно |
| Массовая реактивация пользователей | Churn rate может быть занижен | Добавить метрику reactivation rate |
| Ручная корректировка данных в CSV | Нарушение внутренних связей (например, is_active=False при paid) | Проверить раздел 5 отчёта перед анализом |
| Высокий z-score outliers в churn rate | Аномальные месяцы могут искажать тренд | Исключить выбросы или проанализировать отдельно |
| **Появление новых пользователей после месяца 1** | Активная база может расти; расчёт churned_users становится сложнее | Использовать когортный анализ; проверка монотонности покажет 0 |
| **Изменение тарифа пользователя** | ARPU может меняться из-за апсейлов, а не «вымывания» дешёвых пользователей | Запросить историю изменений тарифа; добавить метрику upgrade/downgrade rate |
| **Разные даты первого платежа у пользователей** | Churn rate, рассчитанный на всю базу, нерепрезентативен | Перейти на когортный анализ (по месяцу прихода) |

### Резюме по допущениям о миграции и новых пользователях
В текущей версии агента **закрытая когортная модель**:
- Все пользователи стартуют одновременно (месяц 1)
- Тариф фиксирован навсегда
- Нет притока новых пользователей
- Нет апсейлов и даунсейлов

Это делает модель идеальной для анализа **старения когорты** и **долгосрочного LTV**, но **непригодной** для анализа:
- Влияния маркетинговых кампаний (требуют новых пользователей)
- Эффективности апсейл-стратегий
- Динамики базы в быстрорастущем сервисе
