
# Agentic Approach: 

## Роль агента

Агент выступает в роли **финансового аналитика подписочного сервиса (SaaS/Fintech)**. Он автоматически:
- генерирует или загружает данные о платежах пользователей;
- рассчитывает ключевые метрики (выручка, отток, ARPU);
- проводит качественные проверки данных;
- формирует структурированный аналитический отчёт с конкретными бизнес-рекомендациями (action items).

---

## Устройство агента

Агент построен по **пайплайн-паттерну**:

| Слой | Назначение |
|------|-------------|
| **Data Layer** | генерация / загрузка данных |
| **Metrics Layer** | расчёт метрик (чистый Python / pandas) |
| **Quality Layer** | 17 автоматических проверок качества |
| **LLM Layer** | вызов LLM через OpenRouter с fallback по моделям |
| **Output Layer** | отчёт + визуализации + экспорт |

---

## Обычные расчёты кодом (не LLM)

- Генерация синтетических данных (распределения, churn probability, payment success rate)
- Расчёт `active_users`, `paid_users`, `churned_users`, `churn_rate`, `monthly_revenue`, `ARPU`
- Все статистические проверки (z-score outliers, монотонность, корректность диапазонов)
- Валидации целостности данных (дубликаты, NULL, mismatches, inconsistent states)
- Визуализация (matplotlib)

---

## Используемые prompts

**Системный промпт:**  
> «Ты — финансовый аналитик подписочных сервисов. Отвечай строго по структуре, кратко и по делу.»

**Пользовательский промпт** содержит 6 обязательных разделов:

1. Executive Summary  
2. Monthly Revenue Trend  
3. Churn Trend  
4. ARPU Trend  
5. Data Quality Checks  
6. Business Interpretation (с action items по приоритетам)

## Guardrails и ограничения

| Guardrail | Контекст / Почему это важно | Описание правила |
|-----------|----------------------------|------------------|
| **Anti-hallucination** | LLM склонна генерировать правдоподобные, но не существующие в данных цифры (например, «выручка выросла на 15%» при отсутствии таких данных). Это критично для финансового анализа, где ложные цифры ведут к неверным бизнес-решениям. | LLM запрещено выдумывать цифры или причины — только из таблицы. |
| **Math safety** | LLM часто ошибается в арифметике (например, считает процент от неправильной базы). В финансовом контексте ошибка в 1% может стоить миллионы. | Запрещены расчёты процентов роста (MoM%, CAGR) — только абсолютные значения из таблицы. |
| **No filler** | Финансовые отчёты должны быть краткими и по делу. «Водные» вступления отвлекают от ключевых выводов и увеличивают время анализа. | Запрещены вступления («Конечно», «Ниже представлен», «Как аналитик, я считаю...»). |
| **Completeness** | LLM имеет тенденцию «экономить» и выдавать неполные ответы, пропуская часть разделов. В финансовом анализе каждый раздел важен для принятия решений. | Сгенерируй все 6 разделов в рамках одного сообщения. Не прерывайся. |
| **Context separation** | Если LLM увидит проблемы в проверках качества (раздел 5), она может начать сомневаться в данных в разделах 1-4. Это блокирует анализ. Для бизнес-выводов данные считаются достоверными, а проверки качества — отдельный контекст. | Проверки качества используются ТОЛЬКО в пункте 5 для оценки достоверности данных. В пунктах 1-4 и 6 данные считаются достоверными (даже если в проверках есть ошибки — это отдельный вопрос). |
| **Causality grounding** | Без привязки к данным LLM начинает объяснять падение выручки внешними факторами («кризис», «конкуренты»), которых нет в данных. Это вводит в заблуждение. | Каждое изменение метрики должно иметь причину из доступных данных. Без причины — только констатация факта. |
| **Actionability constraint** | Анализ без действий бесполезен для бизнеса. Требование конкретных шагов с дедлайнами и метриками успеха превращает отчёт в рабочий документ. | Каждый вывод в Business Interpretation требует формата `ACTION | WHEN | SUCCESS`. |
| **Retry logic** | OpenRouter и бесплатные модели часто возвращают 429 (rate limit) или 402 (требуется оплата). Без retry агент бы падал при первом отказе. | 3 попытки с экспоненциальной задержкой (5 → 10 → 20 сек). |
| **Fallback по моделям** | У разных моделей разные лимиты и доступность. Одна модель может быть перегружена, другая — работать. | Последовательный перебор 8+ бесплатных моделей до первой успешной. |
| **Format enforcement** | LLM имеет тенденцию отступать от требуемой структуры, особенно при длинных ответах. Жёсткое требование разделов обеспечивает парсируемость и единообразие отчётов. | Ответ должен начинаться строго с `## 1. Executive Summary` и содержать все 6 разделов. |

## Контекст для корректной интерпретации метрик и проверок

Для предотвращения ошибок интерпретации со стороны LLM в промпт добавлены детальные определения:

### Определения метрик
| Метрика | Корректное определение |
|---------|------------------------|
| `active_users` | Пользователи с активным аккаунтом в месяце (могут как платить, так и не платить — grace period, проблемы с биллингом) |
| `paid_users` | Пользователи, фактически совершившие успешный платёж в этом месяце (подмножество `active_users`) |
| `churned_users` | Пользователи, активные в предыдущем месяце, но ставшие неактивными в текущем (строгая потеря клиента) |
| `churn_rate_pct` | `churned_users / active_users(prev_month) * 100`. **Не путать с процентом неплатежей** |
| `arpu` | `monthly_revenue / paid_users`. **Важно: не на `active_users`, а именно на `paid_users`** |

### Определения проверок качества (17 проверок)
Каждая проверка сопровождается описанием того, что именно она выявляет:
- `full_duplicates` — полностью дублированные строки (должно быть 0)
- `key_duplicates_user_month` — повтор пары (user_id, month) — критическая ошибка
- `paid_status_amount_mismatch` — при `payment_status='paid'` сумма не равна `monthly_price`
- `paid_users_exceed_active_users` — невозможная ситуация (`paid_users` не может быть больше `active_users`)
- и т.д. для всех 17 проверок

Это позволяет LLM:
- **Не путать метрики** (например, не считать ARPU на всех активных)
- **Правильно интерпретировать проверки** (понимать, что `key_duplicates` — критично, а `statistical_outliers` — может быть нормой)
- **Давать осмысленные рекомендации** (если `paid_status_amount_mismatch > 0` — проблема в биллинге)

## Почему выбран такой подход

| Причина | Обоснование |
|---------|--------------|
| **Надёжность** | Критические расчёты (ARPU, churn rate) делаются кодом, LLM их не трогает. В противном случае LLM имеет склонность сочинять данные. |
| **Экономичность и простота использования** | Использование бесплатных API из открытых источников, Google Colab в качестве интерпретатора. |
| **Контролируемость** | 17 проверок качества данных по различным метрикам. |
| **Безопасность от галлюцинаций** | Жёсткие guardrails запрещают LLM выдумывать цифры. |
| **Бизнес-ориентированность** | Каждый вывод требует конкретный action с измеримым success-критерием. |
| **Отказоустойчивость** | При недоступности одной модели автоматически переключается на следующую по списку (кончились токены, недоступность модели). |
